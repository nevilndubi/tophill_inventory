## 1. System overview

```
                       ┌──────────────────────────────┐
                       │          Browser / Tablet     │
                       └───────┬───────────────▲───────┘
                  HTTPS (pages) │               │ SSE (live status)
                               ▼               │
                  ┌─────────────────────┐      │
                  │  Next.js (Vercel)   │      │
                  │  App Router, RSC    │      │
                  └───────┬─────────────┘      │
          login (JWT)     │ REST + Bearer JWT  │
   ┌──────────────┐       ▼                    │
   │ Supabase     │  ┌────────────────────────┴─────────┐
   │  • Auth      │◄─┤  NestJS API (persistent Node host)│
   │  • Storage   │  │  modules: auth, users, machines,  │
   └──────────────┘  │  usage, bookings, service, ...    │
                     └───┬───────────────┬───────────┬───┘
                         │ Prisma        │ ioredis   │ BullMQ jobs
                         ▼               ▼           ▼
                  ┌────────────┐   ┌──────────────────────┐
                  │ Neon       │   │ Redis                │
                  │ PostgreSQL │   │ cache • pub/sub •    │
                  │ (truth)    │   │ queues • rate limits │
                  └────────────┘   └──────────────────────┘
                                           ▲
                                  ┌────────┴────────┐
                                  │ Worker process  │  (same codebase, `WORKER=true`)
                                  │ reminders, sweeps│
                                  └─────────────────┘
```

**Principles**
1. **Neon is the single source of truth.** Everything else (Redis, UI state) is derivable.
2. **Rules live server-side.** UI mirrors rules; API and DB enforce them.
3. **Vertical modules.** Each NestJS module owns its controller, service, repository access, DTOs and tests.
4. **Fail soft on cache.** Redis down ⇒ slower, not broken.
5. **Boring, explicit, testable.** Prefer simple code over cleverness.

## 2. Component responsibilities

| Component | Responsibility | Notes |
|---|---|---|
| **Next.js web** | UI, routing, forms, calendar, status board, live updates | Talks to NestJS API only for application data (never directly to Neon). Talks to Supabase for Auth session handling and only through API-issued signed Storage upload/download URLs |
| **NestJS API** | All business logic, validation, authorization, persistence, caching, realtime stream | Stateless apart from SSE connections; horizontally scalable via Redis pub/sub |
| **Worker** | BullMQ consumers + schedulers | Same repo/image, started with a different entrypoint. Never serves HTTP traffic |
| **Neon PostgreSQL** | Persistent data, constraints, transactions | Pooled URL for runtime, direct URL for migrations. Branches for dev/staging/CI |
| **Redis** | Cache, pub/sub, BullMQ, rate-limit counters, short locks | TLS in production; every key has a TTL (BullMQ keys excepted) |
| **Supabase Auth** | Invite-only identity (email/password), JWT issuance | Public/anonymous sign-up and magic-link login are disabled; app roles are **not** trusted from the JWT — they come from our `users` table |
| **Supabase Storage** | Machine photos, manuals, service attachments | Private buckets; API issues short-lived signed URLs |
| **GitHub Actions** | CI: lint, typecheck, test, build, migration check, deploy hooks | |

**Why Supabase Auth/Storage but Neon for data (D1):** two Postgres databases would split the data and double the operational burden. Neon stays the one database; Supabase is used only for the services that save us from writing auth and file storage ourselves. If the owner later prefers one vendor, the swap is isolated to the `auth` and `files` modules.

**Why the API is not on Vercel serverless (D4):** SSE streams and BullMQ workers need long-lived processes. Vercel hosts the Next.js app; the API runs on a persistent Node host (Azure App Service recommended).

## 3. Data model

Unless a table is explicitly documented with another key/timestamp shape, tables use `id` (`uuid`, generated by PostgreSQL with `gen_random_uuid()`), `created_at`, and `updated_at` (`timestamptz(3)`, UTC). Prisma's `@updatedAt` supplies `updated_at` automatically on application updates. Soft delete via `deleted_at` where noted.

### 3.1 Tables

**users** — `id`, `supabase_user_id` (nullable, unique), `email` (unique), `full_name`, `role` (enum), `department_id` (nullable FK), `phone`, `is_active`, `is_seed_data`, `last_login_at`

Task 1.7 demo users have `is_seed_data = true` and a null `supabase_user_id`, so they cannot sign
in. A named database check requires every non-seed user to have a Supabase identity and every seed
user to have none. Consequently, Task 2.2 cannot link an existing real row by email without first
weakening that invariant, and it intentionally does not do so. The six reserved `@example.invalid`
placeholders remain inert examples; the Task 2.5 invitation workflow creates separate real rows with
their exact Supabase identities.

User administration never exposes `supabase_user_id`, `is_seed_data` or internal timestamps to the
browser. Lists exclude seed rows, use stable name/ID sorting, search normalized names or email
case-insensitively, and paginate server-side (25 by default, 100 maximum). Email is immutable after
invitation. Full names are trimmed and bounded to 120 characters, and `DEPT_MANAGER` always requires
a department.

**departments** — `id`, `name` (case-insensitively unique through
`departments_name_ci_key`), `code` (case-insensitively unique through
`departments_code_ci_key`), `manager_user_id` (nullable FK)

**locations** — `id`, `department_id` (FK), `name` (e.g. "ICU Bay 3"), `building`,
`floor`, `room`; case-insensitively unique within a department through
`locations_department_id_name_ci_key`

Core-table constraints: user email is normalized to lowercase by a database trigger and protected by
a unique index on `lower(email)`. The two user/department relationships are named independently:
department membership uses `ON DELETE RESTRICT`, while department management uses `ON DELETE SET
NULL`. Locations also use `ON DELETE RESTRICT`, so deleting a department never cascades into users
or locations.

**machine_categories** — `id`, `name` (case-insensitively unique through
`machine_categories_name_lower_key`), `description`, `default_service_interval_days` (nullable),
`default_max_booking_minutes` (nullable). The API applies stricter practical bounds than the
original positive-only database checks: service intervals are 1–3650 days and booking limits are
5–1440 minutes. Category names are Unicode NFC-normalized, trimmed and whitespace-collapsed before
write.

**machines**
- identity: `id`, `asset_tag` (unique, human-readable e.g. `HM-000123`), `name`, `category_id`, `manufacturer`, `model`, `serial_number` (unique per manufacturer), `description`
- placement: `department_id` (owning), `location_id` (current)
- lifecycle: `purchase_date`, `warranty_expires_on`, `commissioned_on`, `retired_on`
- **condition**: `condition` enum — `OPERATIONAL | NEEDS_SERVICE | UNDER_MAINTENANCE | OUT_OF_SERVICE | RETIRED` (default `OPERATIONAL`)
- booking policy: `is_bookable` (bool), `requires_approval` (bool), `allow_booking_when_needs_service` (bool, default false), `max_booking_minutes` (nullable override), `buffer_minutes` (nullable override; cleaning/setup time after each booking)
- service: `service_interval_days` (nullable override), `last_serviced_at`, `next_service_due_at`
- `deleted_at`
- **No `is_in_use` column.** Usage is derived from `usage_sessions` (D2).

Machine identity is database-owned. `asset_tag` defaults from the `machine_asset_tag_seq` sequence
through `next_machine_asset_tag()` and is permanently unique, including after soft deletion.
`manufacturer` and `serial_number` are both required, trimmed and lowercased by a database trigger,
and their pair is permanently unique; a deleted machine's physical serial identity therefore cannot
be re-registered. A machine may use a location owned by a different department because shared
equipment placement is intentional; the department and location foreign keys remain independent.
Nullable booking and service intervals must be positive, retirement date and condition must agree,
and warranty expiry cannot precede commissioning when both dates are known. All machine relations
use non-cascading `ON DELETE RESTRICT` behavior.

Task 3.3 exposes machine registration and registry maintenance through minimized DTOs. Create
requires `name`, `categoryId`, `manufacturer`, `model`, `serialNumber`, `departmentId`, and
`locationId`; location is therefore required by the existing schema. Description, lifecycle dates,
booking-policy overrides, and service fields are optional. Names/manufacturer/model/serial are
bounded to 120 characters, description to 2,000, service intervals to 1–3,650 days, booking limits
to 5–1,440 minutes, and buffers to 1–1,440 minutes. DATE columns accept and return only
`YYYY-MM-DD`; `last_serviced_at` accepts an offset-bearing ISO-8601 instant. Manufacturer and serial
are additionally lowercased after Unicode NFC/whitespace normalization. Clients cannot write asset
tags, condition, retirement/deletion state, `next_service_due_at`, IDs, timestamps, or relation
objects. These API maxima intentionally narrow the Task 1.3 database checks, which require only
positive interval values; the database remains the final lower-bound/race backstop.

Registration relies on the database asset-tag default, so concurrent writers are safe and rolled
back inserts may leave harmless sequence gaps. It atomically creates the first SYSTEM history row
(`NULL -> OPERATIONAL`, reason `Machine registered`) and the `machine.created` audit event.
`next_service_due_at` is calculated in the same write from `last_serviced_at + service_interval_days`,
or cleared when either source is null; Tasks 6.2/6.3 take ownership of
service completion and maintenance schedules. PATCH writes only supplied fields. A semantically
unchanged PATCH is a 200 no-op that neither updates `updated_at` nor writes an audit event; full
optimistic locking remains deferred.

DELETE means removal from the active registry, not a RETIRED condition transition: it locks the
machine row, rejects an open usage session or any PENDING/CONFIRMED/IN_PROGRESS booking, sets only
`deleted_at`, and writes `machine.deleted`. A repeated delete returns 409
`MACHINE_ALREADY_DELETED`. True end-of-life remains the Task 4.1 RETIRED transition. Lists include
RETIRED machines by default but all current list/detail/tag reads hide soft-deleted rows. To close
the opposite side of the race, Task 4.2 checkout and Task 5.3 booking creation must lock the same
machine row and reject a soft-deleted machine.

Task 3.8 completes registry restoration without changing condition state. `POST
/machines/:id/restore` locks the machine row, clears only `deleted_at`, and atomically writes
`machine.restored`; two concurrent restores serialize, so exactly one succeeds and the other gets
`MACHINE_NOT_DELETED`. Delete and restore accept an optional normalized 1–200 character reason,
stored only in the audit payload context. A DELETE request body is supported by the browser,
configured CORS methods/headers and Nest/Express JSON parser. Neither operation writes condition
history or changes `condition`/`retired_on`, and restoration is not blocked by historical bookings,
sessions, tickets, service records, files or history.

Machine lists accept strict `registry=active|deleted|all` (default `active`). Deleted/all lists and
`include_deleted=true` detail reads require `machine:restore`; authorization occurs before resource
lookup. Ordinary detail and asset-tag/QR reads always hide deleted rows. Minimized DTOs expose only
`registryStatus` (`ACTIVE` or `DELETED`), never `deleted_at`. The new `machine:restore` permission is
GLOBAL only for SUPER_ADMIN and ADMIN; `machine:retire` continues to govern registry removal. The
stable restore error is `MACHINE_NOT_DELETED`. Soft-deleted rows retain permanent identity and all
relations, remain counted by reference-data deletion guards, cannot receive attachments, and cannot
be selected for QR labels. Task 7.2 invalidates machine, reference-count and status-board caches on
both registry operations; Task 7.4 emits the corresponding realtime events.

**machine_status_history** — `id`, `machine_id`, `from_condition`, `to_condition`, `reason`, `changed_by_user_id`, `source` (`MANUAL | SERVICE_TICKET | SCHEDULE | SYSTEM`), `ticket_id` (nullable), `created_at`

The first status-history record may have a null `from_condition`; subsequent records are immutable
application history. Machine, actor and optional service-ticket foreign keys use `ON DELETE
RESTRICT`; `machine_status_history_ticket_id_idx` supports ticket-history lookup. The current owner
role must retain migration privileges, so role-level `UPDATE`/`DELETE` revocation for the application
role is deferred to the least-privilege database-role work in Task 10.1. Until then, application code
must expose inserts only; the history model intentionally has no `updated_at`.

**usage_sessions** — `id`, `machine_id`, `user_id`, `booking_id` (nullable), `started_at`, `expected_end_at` (nullable), `ended_at` (nullable), `purpose` (free text, ≤200 chars, **no patient data**), `end_note`
- `usage_sessions_one_open_per_machine`: partial unique index on `machine_id WHERE ended_at IS NULL`
- `usage_sessions_one_per_booking`: partial unique index on `booking_id WHERE booking_id IS NOT NULL`
- Named checks: `usage_sessions_ended_at_not_before_started_at_check`, `usage_sessions_expected_end_after_started_at_check`, and `usage_sessions_purpose_length_check`

**bookings** — `id`, `machine_id`, `requested_by_user_id`, `starts_at`, `ends_at`, `blocked_until`, `status` enum (`PENDING | CONFIRMED | IN_PROGRESS | COMPLETED | CANCELLED | REJECTED | NO_SHOW`), `purpose`, `approved_by_user_id`, `decision_note`, `cancelled_reason`
- Named checks: `bookings_ends_after_starts_check`, `bookings_blocked_until_not_before_ends_check`, and `bookings_purpose_length_check`
- **Overlap guard (raw SQL migration; requires `btree_gist`):**
  ```sql
  CREATE EXTENSION IF NOT EXISTS btree_gist;
  ALTER TABLE bookings
    ADD CONSTRAINT bookings_no_overlap
    EXCLUDE USING gist (
      machine_id WITH =,
      tstzrange(starts_at, blocked_until, '[)') WITH &&
    ) WHERE (status IN ('PENDING','CONFIRMED','IN_PROGRESS'));
  ```
  The API catches Postgres error `23P01` (exclusion violation) and returns `409 BOOKING_CONFLICT` with the conflicting window. At creation, the API stores `blocked_until = ends_at + the machine's effective buffer`; no buffer stores `blocked_until = ends_at`. This is a snapshot, so later machine-policy changes cannot retroactively create conflicts among existing bookings. It is deliberately a stored value rather than a generated expression: PostgreSQL marks `timestamptz + interval` as `STABLE`, and generated expressions require immutable functions. Task 1.4 confirmed this in the live catalog and with a rejected generated-column probe. The half-open `[)` range permits a following booking exactly at `blocked_until`.

Bookings and usage sessions are records of fact and are never hard-deleted by application code. Every foreign key from these tables to machines, users, or bookings uses `ON DELETE RESTRICT`.

**service_tickets** — `id`, `machine_id`, `reported_by_user_id`, `title`, `description`, `severity` (`LOW | MEDIUM | HIGH | CRITICAL`), `status` (`OPEN | ASSIGNED | IN_PROGRESS | RESOLVED | CLOSED | CANCELLED`, default `OPEN`), `assigned_to_user_id`, `type` (`FAULT | PREVENTIVE | CALIBRATION | INSPECTION`), `opened_at` (default now), `resolved_at`, `closed_at`, `machine_out_of_service_from`, `machine_back_in_service_at`
- Title length is 1–200 and whitespace-only titles are rejected; descriptions are limited to 4,000 characters. Stable checks: `service_tickets_title_length_check`, `service_tickets_title_not_blank_check`, and `service_tickets_description_length_check`.
- `RESOLVED`/`CLOSED` require `resolved_at`; `CLOSED` requires `closed_at`; resolution cannot precede opening, closing cannot precede resolution, and return to service cannot precede removal from service. `ASSIGNED`/`IN_PROGRESS` require an assignee. Stable checks use the `service_tickets_*_check` names in the Task 1.5 migration.
- No unique "open fault per machine" constraint exists: preventive, calibration and fault work may coexist, and Task 6.1 owns duplicate-report handling.

**service_records** — `id`, `ticket_id`, `performed_by_user_id`, `performed_at`, `work_done`, `parts_replaced`, `cost_amount` (nullable `integer` minor units), `currency` (default `KES`), `next_due_at`, `vendor_name`
- Tickets may have multiple service records for parts and repeat visits. `service_records_ticket_id_performed_at_idx` preserves ordered retrieval.
- `service_records_cost_amount_nonnegative_check`, `service_records_next_due_after_performed_check`, and `service_records_currency_format_check` enforce non-negative costs, strictly future next-due timestamps, and three-letter uppercase currency codes. PostgreSQL/Prisma `integer` caps one record at 2,147,483,647 minor units (about KSh 21.47 million), sufficient for individual service work.

**maintenance_schedules** — `id`, `machine_id`, `interval_days`, `last_done_at`, `next_due_at`, `is_active` (default true)
- `maintenance_schedules_interval_days_positive_check` and `maintenance_schedules_next_due_not_before_last_done_check` enforce cadence and timestamp ordering.
- `maintenance_schedules_one_active_per_machine` permits historical inactive schedules but only one active schedule per machine. `maintenance_schedules_active_next_due_at_idx` supports the active due-service sweep.

Tickets, service records and schedules are records of fact. Every relation to machines, users,
tickets and machine status history uses `ON DELETE RESTRICT`; users are deactivated rather than hard
deleted.

**attachments** — `id`, `entity_type` (`MACHINE | TICKET`), `entity_id` (UUID), `storage_path`, `file_name`, `mime_type`, `size_bytes`, `uploaded_by_user_id`, timestamps
- `entity_type` is the only closed support-table type and therefore uses the PostgreSQL/Prisma `attachment_entity_type` enum. The `(entity_type, entity_id)` relation is polymorphic, so the database deliberately has no invalid cross-table foreign key; Task 3.5/6.6 services must validate the referenced machine/ticket in the same transaction before insert.
- `storage_path` is permanently unique. `attachments_size_bytes_check` requires 1 byte–10 MiB, while `attachments_mime_type_allowed_check` permits `image/jpeg`, `image/png`, `image/webp`, and `application/pdf`; widening this defence-in-depth list requires a migration.
- `attachments_uploaded_by_user_id_fkey` uses `ON DELETE RESTRICT`, and `attachments_entity_type_entity_id_idx` supports entity galleries. There is no soft delete: a permitted delete removes both the row and stored object, while the audit log retains the history.

**notifications** — `id`, `user_id`, `type` (text), `title`, `body`, nullable `entity_type`/`entity_id` pair, `read_at`, `emailed_at`, timestamps
- `type` uses the shared event format (`^[a-z0-9._]{1,64}$`); the shared Zod package owns the evolving allowed identifiers instead of a PostgreSQL enum. Title/body are nonblank and limited to 200/4,000 characters. Entity references must be both null or both present.
- `read_at` and `emailed_at` cannot precede `created_at`. `notifications_user_id_read_at_idx` supports the documented inbox lookup, and partial `notifications_unread_user_id_created_at_idx` supports newest-first unread/bell-count queries. The user FK uses `ON DELETE RESTRICT`.

**notification_preferences** — composite primary key (`user_id`, `type`), `in_app` (bool, default true), `email` (bool, default true), timestamps
- The composite key prevents duplicate per-user/per-type rows without a surrogate ID. `type` follows the same shared text contract as notifications. The critical-alert override is dispatcher logic in Task 9.4, not a database constraint; the user FK uses `ON DELETE RESTRICT`.

**audit_logs** — `id`, nullable `actor_user_id`, `action` (text), `entity_type` (text), `entity_id` (text), `before` (jsonb), `after` (jsonb), `ip` (`inet`), `request_id`, `created_at`
- Nullable actors support background/system work; string entity IDs support non-UUID entities such as `app_settings` keys. Action/entity identifiers use the lowercase shared event format, while request/entity IDs are bounded nonblank text.
- Before/after payloads must be JSON objects or JSON null and together occupy at most 65,536 bytes. The native `inet` type validates optional IPv4/IPv6 addresses.
- `audit_logs_append_only` invokes `prevent_audit_log_mutation()` before every row UPDATE/DELETE and raises SQLSTATE `55000`. The actor FK is `ON DELETE RESTRICT`. Direct privilege revocation remains Task 10.1 because the migration owner can still disable the trigger; integration cleanup therefore leaves audit rows in the disposable branch and deletes that branch instead of bypassing the trigger.
- Stable indexes are `audit_logs_entity_type_entity_id_created_at_idx`, `audit_logs_actor_user_id_created_at_idx`, and `audit_logs_created_at_idx`, all with newest-first timestamps.

**app_settings** — `key` (string PK), `value` (jsonb), timestamps
- The migration idempotently inserts plain JSON-number defaults with `ON CONFLICT (key) DO NOTHING`: `booking.max_duration_minutes = 240`, `booking.min_lead_minutes = 15`, `booking.no_show_grace_minutes = 15`, and `checkout.adhoc_guard_minutes = 30`. These conservative local defaults cap a booking at four hours, require 15 minutes' lead, allow 15 minutes before no-show handling, and protect the next booking for 30 minutes from ad-hoc checkout.
- Task 5.1 validates each key's JSON value shape and exposes settings management; the database only enforces the stable namespaced key format now.

### 3.3 Seed dataset and index review

`prisma/seed.ts` owns deterministic, idempotent demonstration data: 5 Kenyan hospital departments,
20 locations, 8 equipment categories, 60 machines, 6 non-authenticating placeholder users, and
representative bookings, usage sessions, condition history, service tickets, service records, and
maintenance schedules. Fixed IDs and natural-key upserts make reruns update instead of duplicate.
Dates are refreshed relative to the run, purpose text is generic and contains no patient data, and
the machine mix is 45 operational (9 currently in use), 6 needing service, 5 under maintenance, 2
out of service, and 2 retired. Every non-operational machine has matching history and an open
ticket. Explicit `HM-000001`–`HM-000060` tags are followed by a guarded `setval` call that never
moves `machine_asset_tag_seq` backwards.

Seeding requires an explicitly allowed branch and exact host, plus a list of protected `main` and
`staging` hosts. It is disabled in CI. The guarded live path allows `dev` and disposable
`ci/`, `test/`, `ephemeral/`, or `demo/` branches only. `prisma migrate reset` is destructive and
development-only; it must never target `main` or `staging`.

Task 1.7 reviewed the complete migration chain and the five main future query shapes with
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` on both the 60-machine seed and a transaction-scoped
3,000-machine fixture. On the large fixture, machine list and status board queries used
`machines_department_id_idx` (the board also used `usage_sessions_one_open_per_machine`),
availability used `bookings_no_overlap` plus machine identity lookup, My Bookings used
`bookings_requested_by_user_id_starts_at_idx`, and the technician board used
`service_tickets_assigned_to_user_id_status_idx`. The realistic fixture produced no sequential
scan of the primary queried tables, so no speculative index was added. Small seeded tables may use
sequential scans when the planner correctly estimates that cheaper.

Task 3.3 re-ran the concrete machine list/filter/search plans after API implementation on the seed
plus a 3,000-machine disposable fixture. The due-service combination used
`machines_next_service_due_at_idx`; deterministic asset-tag ordering could make the asset-tag
unique index the cheapest path for a broad department result. Selective substring searches over
name, asset tag, and serial number remained sequential at 3,060 rows because PostgreSQL estimated
that cheaper than the existing trigram GIN indexes. This is an expected small-table planner choice,
not evidence for a speculative replacement index; the existing `gin_trgm_ops` indexes remain the
documented large-cardinality path.

Task 4.3 exercised the implemented live-status statement against 500 active-registry machines.
The statement used one database round trip, and its per-machine next-booking lookup selected the
existing `bookings_no_overlap` GiST index; PostgreSQL estimated it cheaper than the separate
`bookings_machine_id_starts_at_idx` btree for this data distribution. The default 50-row request
completed in 145.68 ms end to end against remote Neon, while the database execution portion was
5.88 ms; 200 rows took 152.35 ms, search 136.74 ms, and an `IN_USE` filter 147.04 ms. The linear
plan estimate for 5,000 machines is about 58.83 ms of database execution. No index was added:
Task 7.2 owns caching and Task 7.4 replaces polling pressure with realtime invalidation.

## 4. State machines

### 4.1 Machine condition
The complete allowed-transition table is:

| From | Allowed targets |
|---|---|
| `OPERATIONAL` | `NEEDS_SERVICE`, `UNDER_MAINTENANCE`, `OUT_OF_SERVICE`, `RETIRED` |
| `NEEDS_SERVICE` | `OPERATIONAL`, `UNDER_MAINTENANCE`, `OUT_OF_SERVICE`, `RETIRED` |
| `UNDER_MAINTENANCE` | `OPERATIONAL`, `OUT_OF_SERVICE`, `RETIRED` |
| `OUT_OF_SERVICE` | `UNDER_MAINTENANCE`, `RETIRED` |
| `RETIRED` | `UNDER_MAINTENANCE` (reinstate for inspection) |

Every other pair returns `INVALID_TRANSITION`. All transitions require `service:manage`; crossing
into or out of `RETIRED` additionally requires `machine:retire`, checked through the shared
permission helper. Entering retirement sets `retired_on` to the Africa/Nairobi calendar date;
reinstatement clears it. Registry deletion/restoration remains independent and never changes
condition or retirement date.

Transitions are validated only by `ConditionService.transition()`, inside a transaction that locks
the machine row. A successful transition atomically updates the machine, appends immutable
`machine_status_history`, records `machine.condition_changed`, and emits a typed in-process event
only after commit. Manual requests carry the condition observed by the client and fail with
`CONDITION_CHANGED` if it is stale.

An open usage session does not block `NEEDS_SERVICE`. It always blocks `UNDER_MAINTENANCE` and
`RETIRED`. `OUT_OF_SERVICE` is allowed while in use only with an explicit forced safety transition
and a reason of at least ten characters; the session is never ended or altered. Check-in therefore
remains valid in any condition, while Task 4.2 rejects new check-outs for an ineligible condition.

### 4.2 Usage (derived)
- `IN_USE` ⇔ ∃ `usage_sessions` row with `ended_at IS NULL` for the machine.
- Usage applies to every machine; `is_bookable` governs bookings only. Check-out requires
  `OPERATIONAL`, or `NEEDS_SERVICE` with `allow_booking_when_needs_service`; every other condition
  is unavailable. A soft-deleted machine is indistinguishable from a missing machine.
- Check-out and check-in lock the machine row first with a three-second PostgreSQL `lock_timeout`,
  then read deleted/condition/session state. Lock timeout returns retryable `MACHINE_BUSY`. Task 5.3
  must use the same order: machine row, then bookings/sessions. A single transaction-scoped
  PostgreSQL `now()` supplies session timestamps, expected-end validation and booking-guard time.
- `expected_end_at`, when supplied, is 1 minute–24 hours after that database time. An omitted
  purpose persists the non-PHI default `General equipment use`; supplied purpose is normalized and
  limited to 200 characters. No booking is linked or transitioned in Task 4.2; Task 5.5 owns that
  behavior.
- Ad-hoc check-out rejects another user's `CONFIRMED` booking when `starts_at <= boundary` and
  `blocked_until > now`, where `boundary` is the later of the setting-driven guard boundary and the
  supplied expected end. The inclusive start makes a booking exactly at the boundary block while a
  booking one millisecond later does not. Already-started, still-blocked bookings remain protected;
  the caller's own bookings and `PENDING` bookings do not block. `checkout.adhoc_guard_minutes` must
  be an integer 0–240; missing/invalid data fails closed as `SETTINGS_INVALID`.
- Ordinary check-in closes only the holder's session and remains valid in every machine condition.
  A non-holder must explicitly request force-end, provide a 10–200 character reason and hold
  `usage:force-end`; SUPER_ADMIN/ADMIN are global and DEPT_MANAGER is limited to the locked
  machine's owning department. Forced condition changes never end sessions.
- Usage audits use entity type `usage_session` and the session ID; machine ID and forced/reason/note
  context are stored without identity addresses. The session row intentionally does not identify
  who ended it; the append-only audit row does. Check-out/check-in/force-end events are emitted only
  after commit for Task 7.4. Booking linking and status transitions remain Task 5.5.

### 4.3 Display status (computed, `StatusService`)

`StatusService` is the sole application boundary for derived live status. It persists no display
status or `is_in_use` value. Its exact priority is `RETIRED` → `OUT_OF_SERVICE` →
`UNDER_MAINTENANCE` → `IN_USE` → `AVAILABLE_NEEDS_SERVICE` → `AVAILABLE_OK`; usage is true only
when an open `usage_sessions` row exists. A shared browser-safe contract owns this enum, order,
labels, the mapping to all six existing icon/text/colour styles, and `isMachineUsable()`. Both the
status service and Task 4.2 checkout use that same usability predicate: condition must be
`OPERATIONAL`, or opted-in `NEEDS_SERVICE`, and no session may be open. Caller-specific booking
guards are intentionally not part of `usable`.

`GET /api/v1/machines/:id/status` and `GET /api/v1/status/board` require `machine:read`, return
`Cache-Control: no-store` and `Vary: Authorization`, and hide soft-deleted machines. RETIRED rows
remain visible. Responses contain minimized machine/category/department/location data, condition,
derived status, `usable`, `service_due`, `next_booking_at`, `open_session`, and `as_of`. The open
session is returned even when a higher-priority condition wins; it exposes only session ID, holder
ID/full name, start/expected-end, current-user ownership and overdue state. `service_due` is false
for RETIRED and otherwise means a non-null due time at or before `as_of`. `next_booking_at` is the
earliest strictly-future `CONFIRMED` start and never exposes the requester.

One parameterized SQL statement supplies the board data, total, and six complete counts. A
materialized request clock gives every calculation one PostgreSQL timestamp. A CASE expression
derives status; the open session is joined through its partial unique index; a bounded LATERAL
lookup finds the next confirmed booking; relation and holder data are joined without N+1 reads.
The single-machine endpoint reuses the same query builder. Board filters are strict:
`department_id`, `category_id`, `location_id`, repeatable `status`, escaped 2–100 character `q`,
`service_due=true`, `page`, `page_size` (50 default, 200 maximum), `sort=asset_tag|name|status`, and
`order=asc|desc`. Status sorting uses this priority then asset tag and ID; other sorts also end in
an ID tie-breaker. `counts` apply every filter except `status` and include zeros for all six states;
`total` applies the status filter too.

### 4.4 Booking
```
PENDING ──approve──► CONFIRMED ──check-in──► IN_PROGRESS ──check-in complete──► COMPLETED
PENDING ──reject──► REJECTED
PENDING/CONFIRMED ──cancel──► CANCELLED
CONFIRMED ──grace period passes without check-in──► NO_SHOW   (worker job)
```
Machines with `requires_approval = false` create bookings directly as `CONFIRMED`.

### 4.5 Service ticket
`OPEN → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED` (+ `CANCELLED`). Coupling to machine condition is performed by `ServiceService` calling `ConditionService.transition()`; it never writes `machines.condition` directly.

## 5. API design

- **REST, JSON, versioned:** application routes use `/api/v1/...`; root-level `/health` and `/health/ready` are explicit exceptions for infrastructure probes. OpenAPI is at `/api/docs` (non-production or Admin-only in production).
- **Auth:** application routes accept only `Authorization: Bearer <Supabase JWT>`. A global guard verifies the asymmetric Supabase JWKS signature and `kid`, permits only ES256, requires the exact issuer, `aud = authenticated`, `role = authenticated`, an unexpired token and a UUID subject, with 30 seconds of clock tolerance. No shared JWT secret is stored. The subject must match an existing active, non-seed `users.supabase_user_id`; there is no email linking or automatic provisioning. The sole exception is the guarded, transactional first-SUPER_ADMIN bootstrap described below. Root health probes and non-production Swagger are explicitly public; CORS preflight bypasses authentication. A JWKS/provider outage returns `AUTH_UNAVAILABLE` with HTTP 503 instead of treating the session as invalid. The user's **role and active flag come from Neon**, with Redis caching deferred to Task 7.2.
- **Authorization:** the authentication guard runs first and loads the active Neon user; the global permission guard then requires exactly one of `@RequirePermission(...)`, `@AuthenticatedOnly()` or `@Public()`. It fails closed for absent/unknown metadata or roles and returns `403 PERMISSION_DENIED` without identifying allowed roles. Application roles and departments come only from that Neon user context, never JWT claims or request input. The permission map and browser-safe `can`/`getPermissionScope` helpers live in `packages/shared`; scoped services use the API's department helpers before reading or mutating resources.
- **Validation:** shared Zod schemas; unknown fields stripped/rejected.
- **Errors (standard shape):**
  ```json
  { "error": { "code": "BOOKING_CONFLICT", "message": "…", "details": { }, "requestId": "…" } }
  ```
- **Pagination:** cursor or `page`/`pageSize` (max 100) with `total`; **filtering/sorting** via query params; consistent envelope `{ data, meta }`.
- **Idempotency:** `POST /bookings` accepts `Idempotency-Key` header (stored in Redis 24h) to survive double-taps on flaky hospital Wi-Fi.
- **Time:** ISO-8601 UTC in/out.

Task 3.3 machine reads use `page`/`pageSize` (25 by default, 100 maximum), return `meta.total`, and
allow only `asset_tag`, `name`, `manufacturer`, `serial_number`, `condition`, or
`next_service_due_at` sorting with an ID tie-breaker. Filters are `department_id`, `category_id`,
`location_id`, `condition`, `is_bookable`, and `service_due`; the latter means a non-null due instant
at or before the request's current UTC time. `is_bookable` is the stored policy flag, not effective
availability. Search is case-insensitive across name/tag/serial, parameterized with SQL wildcard
characters escaped, and accepts 2–100 trimmed characters. One-character terms are rejected; two-
character terms are permitted for exact operational usefulness but commonly use a sequential plan,
while trigram selectivity becomes useful from three characters onward. Every unknown query/body
field is rejected.

Stable machine errors are `MACHINE_NOT_FOUND`, `MACHINE_IDENTITY_TAKEN`,
`MACHINE_CATEGORY_NOT_FOUND`, `MACHINE_DEPARTMENT_NOT_FOUND`, `MACHINE_LOCATION_NOT_FOUND`,
`MACHINE_ALREADY_DELETED`, `MACHINE_HAS_OPEN_SESSION`, `MACHINE_HAS_ACTIVE_BOOKINGS`,
`MACHINE_NOT_DELETED`, `MACHINE_DATES_INVALID`, and `MACHINE_VALUES_INVALID`. Prisma unique/FK/check failures are mapped to
these contracts without exposing database metadata. `machine.created`, `machine.updated`, and
`machine.deleted`/`machine.restored` audit snapshots contain business fields and relationship IDs
only; optional registry reasons are nested in their audit context.

Condition errors are `MACHINE_DELETED`, `INVALID_TRANSITION`, `CONDITION_UNCHANGED`,
`CONDITION_CHANGED`, `MACHINE_HAS_OPEN_SESSION`, and `CONDITION_FORCE_INVALID`. History is newest
first, page-based (50 by default, 200 maximum), includes the registration row, and returns only
from/to condition, source, reason, timestamp, and actor full name. Deleted-machine history follows
the same `include_deleted=true` plus `machine:restore` rule as deleted detail reads.

Usage errors are `MACHINE_NOT_FOUND`, `MACHINE_NOT_AVAILABLE`, `MACHINE_IN_USE`,
`UPCOMING_BOOKING_CONFLICT`, `NO_OPEN_SESSION`, `SESSION_NOT_HELD`, `FORCE_NOT_APPLICABLE`,
`EXPECTED_END_INVALID`, retryable `MACHINE_BUSY`, retryable `SETTINGS_INVALID`, and
`PERMISSION_DENIED`. The one-open-session partial unique index remains the race authority.
`MACHINE_IN_USE` identifies the current caller's own session with a boolean and otherwise returns
only holder ID/full name plus safe timing metadata. Booking conflicts return only the earliest start
and whether it already began. Responses never contain addresses or authentication fields.

Task 3.7 adds `GET /machines/import/template` and `POST /machines/import`, both protected by
`machine:create` (SUPER_ADMIN and ADMIN only). Version `v1` is comma-delimited UTF-8 with an exact
19-column contract; uploads are streamed only as far as the 1 MiB limit, limited to 1,000 data rows
and 500 characters per cell, and parsed with `csv-parse` using BOM, quoted-field and bounded-record
support. Category, department and location reference maps are loaded once, and existing normalized
manufacturer/serial identities are queried once. Formula-like cells are preserved on input with a
warning and escaped by the shared spreadsheet-safety helper whenever emitted to CSV.

Dry run is the default and writes nothing. Its report returns normalized row previews, errors,
warnings, status counts, template version and a SHA-256 of the exact bytes. Commit and partial modes
upload and validate the file again and require that preview hash (`IMPORT_FILE_CHANGED` otherwise).
A full import is one 60-second transaction, writes in 100-row set-based chunks in file order and
rolls every machine/history/audit row back on a database race. Partial mode never writes rejected
rows and uses conflict-safe inserts, reporting race losers as `skipped_conflict`. Existing active
and soft-deleted identities are idempotent skips and are never updated. Each created machine keeps
Task 3.3 registration behavior and receives `machine.created` with `source: import`; one
`machine.import_completed` event contains aggregate counts only. Safe retry guidance is: preview
again after any file edit or full-import conflict; partial mode may be retried because permanent
identity matching prevents duplicates.
Fatal stable codes are `IMPORT_INVALID_CSV`, `IMPORT_FILE_TOO_LARGE`, `IMPORT_TOO_MANY_ROWS`,
`IMPORT_DUPLICATE_HEADERS`, `IMPORT_INVALID_HEADERS`, `IMPORT_INVALID_ROWS`,
`IMPORT_FILE_CHANGED`, and `IMPORT_CONFLICT`. Row reports use `IMPORT_FIELD_INVALID`,
`IMPORT_DUPLICATE_IDENTITY`, reference-specific not-found codes and
`IMPORT_REFERENCE_AMBIGUOUS`; no database or constraint metadata is exposed.

Task 3.5 machine files live in the private `machine-attachments` Supabase Storage bucket. Listing
and five-minute signed downloads require `machine:read`; signed upload, confirmation and deletion
require `attachment:upload`. Signed-upload URLs have Supabase's fixed two-hour lifetime, so the API
adds a signed 15-minute intent binding the randomized server path, machine, actor, declared type,
size and display name. Confirmation reads Storage metadata and bytes, checks size/type plus JPEG,
PNG, WebP or PDF magic bytes, and only then creates the Neon row and `attachment.uploaded` audit in
one transaction. At most 20 attachments are allowed per machine. List responses never contain a
storage path or URL; individual download URLs expire after 300 seconds.

Deletion commits the Neon row removal and `attachment.deleted` audit first, then removes the private
object. A failed object removal is harmless to users and logs `ORPHANED_STORAGE_OBJECT` with the
attachment ID only. The read-only `storage:reconcile` command reports object IDs/counts for objects
older than 24 hours that have no Neon row; `--delete` is an explicit operator action. Task 9.2 will
schedule it. Soft-deleted machines expose none of their files, but machine soft deletion does not
delete file rows or objects so Task 3.8 can restore them with the machine.

## 6. Redis usage (all uses, with rules)

| Use | Key pattern | TTL | Invalidation / notes |
|---|---|---|---|
| Status board snapshot | `board:v1:{filterHash}` | 15–30s | Deleted on any condition change, check-in/out, booking state change (use key-set `board:keys` or version counter `board:ver` to invalidate by bumping version) |
| Machine detail | `machine:{id}:v1` | 5 min | Task 7.2 deletes it on update/delete/restore/condition/usage change; create/update/delete/restore also invalidate future machine-list/status-board/reference-count key sets, and asset-tag lookup keys if introduced |
| Machine status (single) | `status:{id}` | 30s | Same triggers as board |
| Reference data (categories, departments, locations) | `ref:{type}:v1` (`ref:departments:v1`, `ref:locations:v1`) | 10 min | Deleted on every successful write when Task 7.2 adds cache-aside behavior |
| Availability grid | `avail:{machineId}:{date}` | 30s | Deleted on booking change for that machine |
| User + role lookup | `user:{supabaseId}` | 60s | Deleted on role/active change |
| Rate limiting | `rl:{route}:{userOrIp}` | window | Via Nest throttler Redis storage; stricter limits on auth-adjacent and booking endpoints |
| Idempotency keys | `idem:{userId}:{key}` | 24h | Stores response for replay |
| Booking contention lock | `lock:booking:{machineId}` | 5s | Optional short lock to reduce DB conflict storms. **Never a correctness mechanism — the DB constraint is** |
| Pub/Sub channel | `events:machine`, `events:booking`, `events:ticket` | n/a | API instances publish; every instance subscribes and forwards to its SSE clients |
| BullMQ queues | `bull:*` | n/a | Notifications, reminders, sweeps |

**Rules**
1. **Cache-aside only:** read → miss → DB → set. Writes go to DB first, then invalidate.
2. **Invalidate on write, TTL as safety net.** Short TTLs on anything status-related; staleness must never exceed ~30s for status data.
3. **Graceful degradation:** a `CacheService` wrapper catches all Redis errors, logs a warning, and falls through to the database. Circuit-break after repeated failures. `/health/ready` reports Redis state but Redis being down yields `degraded`, not `down`.
4. **Namespaced + versioned keys** (`:v1`) so a bad cache shape can be abandoned by bumping the version.
5. **No PHI, no secrets, no raw JWTs in Redis.**
6. **Serialize with JSON**, keep values small (<100 KB), and never cache per-user permission decisions longer than 60s.
7. Environment prefix (`prod:`, `stg:`) so environments never share keys.
8. Redis hosting: managed Redis with TLS (Azure Cache for Redis or Redis Cloud). Serverless-priced Redis (e.g. Upstash) is fine for cache-only but gets expensive with BullMQ polling — check before choosing.

**Connection foundation (Task 0.7):** the NestJS Redis module starts its ioredis connection in the background, disables the offline command queue, caps reconnect backoff at 2 seconds, and applies 1-second connection, command and readiness timeouts. Development defaults to `redis://127.0.0.1:6379`; production validation requires an explicit `rediss://` URL and enables TLS. Connection lifecycle events are logged without the URL or credentials. Shutdown attempts `QUIT` when ready and otherwise disconnects immediately. The readiness probe returns HTTP 200 with overall status `degraded` and `checks.redis = down` when Redis cannot answer; liveness and API startup are independent of Redis.

**Database readiness bound (Task 3.6 maintenance):** `READINESS_DB_TIMEOUT_MS` bounds the Postgres readiness query and initial adapter connection. It defaults to 3000 ms and validation caps it at 10000 ms so Neon has a practical scale-to-zero wake window without allowing readiness to hang. Liveness remains independent of the database.

The matrix is encoded once in `packages/shared/src/permissions.ts` and consumed by both API guards and UI visibility checks.

The stable permission names are `machine:read`, `machine:create`, `machine:update`,
`machine:retire`, `machine:restore`, `reference:manage`, `attachment:upload`, `booking:create`, `booking:approve`,
`usage:check-in-out`, `usage:force-end`, `fault:report`, `service:manage`, `user:manage`,
`audit:read` and `report:read`. Each role has an explicit entry for every permission—there is no
implicit role inheritance. Scope is one of `GLOBAL`, `OWN_DEPARTMENT` or `NONE`. The three initial
department-scoped grants are `booking:approve`, `usage:force-end` and `report:read` for
`DEPT_MANAGER`; a manager without a department and a resource without a department are denied.
`departmentScopeFilter(user, permission)` supplies list-query scoping and
`assertDepartmentAccess(user, resourceDepartmentId)` enforces single-resource access. The helpers
reserve an optional authorization context so later ownership rules can add `isOwner` without
breaking existing callers; no ownership grant is inferred in Task 2.3.

`@AuthenticatedOnly()` is reserved for identity endpoints such as `GET /me`; every other
non-public application handler declares a permission. Authorization denials use the standard
request-ID error envelope and log only user ID, Neon role, permission, route and request ID. CORS
preflight and the explicitly public infrastructure routes bypass both guards. The Task 2.5 user
policy helpers separately enforce that only SUPER_ADMIN may manage SUPER_ADMIN, ADMIN may assign
non-SUPER_ADMIN roles, nobody else assigns roles, self-deactivation is forbidden and the final
active SUPER_ADMIN is protected.

User invitations validate authorization and local uniqueness before creating the Supabase identity,
then create the matching non-seed Neon row and `user.invited` audit event. If the Neon transaction
fails, the API deletes only the identity created by that request; a failed compensation returns a
5xx, logs only the identity ID with `ORPHANED_AUTH_IDENTITY`, and is discoverable through the
read-only `users:reconcile-auth` command. A pre-existing Auth identity without a Neon row is never
auto-linked (`AUTH_IDENTITY_EXISTS`); it requires an explicit operator reconciliation. Concurrent
duplicates settle through the database email uniqueness rule, with compensation by the losing
request.

Role, department, activation and deactivation mutations lock the active real SUPER_ADMIN rows before
evaluating the last-admin rule. Nobody can change their own role/department or deactivate
themselves; ADMIN cannot modify SUPER_ADMIN; seed rows cannot be listed or mutated. User mutation
and a minimal audit event commit in one Neon transaction. Deactivation is Neon-only: the identity
may still obtain a Supabase session, but every API call receives `USER_INACTIVE` until reactivation.
No Supabase ban/sign-out operation is added, avoiding a second cross-system failure boundary.

Until Task 7.2, the local user (including role, department and active state) is read from Neon on
every request, so changes take effect immediately on the next request. Task 7.2 must preserve that
behavior by invalidating `user:{supabaseId}` whenever role, department or active state changes.

## 8. Realtime design

- **Transport:** Server-Sent Events (`GET /api/v1/stream`) — one-way, simple, proxy-friendly.
- **Flow:** a mutation commits to Neon → service publishes a small event (`{type, machineId, version, at}`) to Redis → every API instance forwards to connected clients → the web app invalidates the relevant TanStack Query keys (or patches the cache) and refetches.
- **Events carry IDs, not data** — clients refetch through normal authorized endpoints, so realtime cannot leak data.
- **Resilience:** heartbeat every 25s, `Last-Event-ID` support, client auto-reconnect with backoff; if SSE fails the UI falls back to 30s polling.
- **Scale note:** one process handles thousands of SSE connections; Redis pub/sub makes multi-instance safe.

## 10. Frontend architecture

- **Next.js App Router** with route groups: `(auth)/login`, the current `(app)/` dashboard placeholder, and planned `(app)/machines`, `(app)/machines/[id]`, `(app)/status`, `(app)/bookings`, `(app)/service`, `(app)/reports`, `(app)/admin/{users,reference,audit,settings}`, `/scan/[assetTag]` (QR landing).
- **Data fetching:** TanStack Query against the typed API client; server components for initial page shells; **no business rules in the client**.
- **API URL handling:** the client is configured with a validated API origin, sends infrastructure checks such as `/health` to that root origin, and prepends `/api/v1` only for application requests. Browser calls use the validated `NEXT_PUBLIC_API_URL`; server-only calls use `API_BASE_URL`. The browser provider reads/refreshes the current Supabase session, while server calls receive the request-scoped validated bearer.
- **Forms:** React Hook Form + shared Zod schemas.
- **Auth:** `@supabase/ssr` creates a browser singleton and one server client per request. Next.js 16 `proxy.ts` calls validated `getClaims()` to refresh cookies and perform only optimistic redirects; it never trusts `getSession()` for a security decision. A cached server DAL validates claims again at each protected leaf/data boundary, retrieves the bearer only after that check, and bootstraps the application context exclusively from API `GET /me`. The NestJS API remains authoritative for identity, active state, role and department.
- **Session and API failures:** a protected API 401 triggers exactly one Supabase refresh/retry, then clears the Supabase session and the entire TanStack Query cache before redirecting to login. `403 PERMISSION_DENIED` keeps the session and shows `/forbidden`; `USER_NOT_PROVISIONED` and `USER_INACTIVE` show `/no-access` with sign-out; `503 AUTH_UNAVAILABLE` and network failures retain the session and show a retryable unavailable banner/page. Supabase auth-state changes clear cached data and propagate sign-out across tabs.
- **Bearer boundary:** access tokens stay inside Supabase clients, are never stored in application React state or localStorage by application code, and are attached only to the exact validated API origin. Server calls obtain the bearer from their request-scoped server client after `getClaims()` succeeds.
- **Navigation:** one typed config maps every item to a `@app/shared` permission and renders it through `can()`/`getPermissionScope()` without role inheritance. Until their feature tasks land, visible future destinations are disabled “coming soon” items; overview and the permission-guarded `/admin` user-management workspace are the implemented links.
- **User management:** `/admin` supplies accessible search/filter/pagination, invitation, role/department editing and activation controls with responsive table/card layouts. UI controls mirror the shared policy helpers, but the API remains authoritative. Invite acceptance uses the server `/auth/confirm` route to exchange a one-time `token_hash` with `verifyOtp`, then an authenticated set-password page enforces the hosted 12-character minimum and follows only validated same-origin return paths.
- **Reference data:** `/admin/reference` starts with category management and is structured for the
  department/location sections added by Task 3.2. Reads require `machine:read` (held by all six
  active roles); mutations and eligible-manager discovery require `reference:manage`. Category list
  `machine_count` includes non-retired, non-deleted machines, while deletion state/count considers
  every database reference. Department and location counts used for deletion likewise include
  retired and soft-deleted machines and are fetched through grouped queries rather than N+1 reads.
  A department manager must be an active, non-seed `DEPT_MANAGER` assigned to that same department;
  the candidate row is locked while a changed manager is validated. User deactivation, movement to
  another department, or a role change away from `DEPT_MANAGER` clears an existing manager reference
  and audits that change in the same transaction. Existing stale managers do not prevent unrelated
  department edits. Location ownership is immutable after creation because re-parenting would alter
  historical placement/report meaning; department codes remain editable and are presented with an
  explicit reporting warning. Task 3.2 errors are `DEPARTMENT_NAME_TAKEN`,
  `DEPARTMENT_CODE_TAKEN`, `LOCATION_NAME_TAKEN`, `DEPARTMENT_NOT_FOUND`, `LOCATION_NOT_FOUND`,
  `DEPARTMENT_IN_USE`, `LOCATION_IN_USE`, `MANAGER_NOT_ELIGIBLE`, `USER_NOT_FOUND`, and
  `LOCATION_DEPARTMENT_IMMUTABLE`.
- **Machine registry UI:** `/machines` consumes the shared Task 3.3 contracts through one paginated
  list request plus cached category/department/location lookups. Validated URL parameters own
  search, filters, sort and pagination so refresh, history and shared links reproduce the same
  view. Desktop tables and mobile cards show only the stored condition using icon + text + colour;
  usage-derived “Available/In use” language waits for Phase 4. Detail routes keep Overview live and
  preserve accessible, URL-addressable “Coming soon” tabs for Status, Bookings, Service and History.
  Files is a private attachment gallery in Task 3.5 with five-minute image/PDF links and direct
  signed uploads; read-only roles can view while `attachment:upload` controls upload/delete actions.
  Task 3.8 adds the administrator-only, URL-persisted Active/Deleted/All registry filter and
  confirmation flows for removal/restoration. Removed rows and details use icon + text + colour,
  hide files and QR/label access, and explain that registry removal is not retirement; restoring
  makes the same files and QR route visible again without altering history.
  Task 4.1 makes Status and History functional: the Status tab renders only transitions allowed by
  the current condition and shared permissions, collects a PHI-safe reason, and reveals the forced
  out-of-service safety path only after an open-session conflict. History is accessible, paginated,
  newest first, and shows safe actor/source metadata. Removed machines show condition read-only.
  Create/update visibility comes directly from `can()` (`machine:create` / `machine:update`),
  while API authorization remains authoritative. DATE values are formatted from their plain parts,
  timestamps use Africa/Nairobi, and `next_service_due_at` stays a labelled read-only calculation.
  Task 3.4 Playwright runs against the real Next routes with a development-only auth seam and
  browser-intercepted API responses; production builds cannot enable that seam.
- **Asset labels and scan lookup:** QR labels are rendered in-browser as black-on-white SVG with error correction M and a four-module quiet zone; no third-party QR service receives data. The validated path-free `NEXT_PUBLIC_APP_ORIGIN` plus canonical upper-case asset tag forms the only QR payload. Print CSS provides a 100 mm × 50 mm single label and 3 × 8 A4 sheets of 70 mm × 37 mm cells with a configurable top offset and alignment test. Bulk selection is session-only, capped at 48, excludes retired/deleted machines, and reuses list data or one matching-list request. All `machine:read` roles may print. `/scan` and `/scan/[assetTag]` are authenticated/noindex, show only the stored condition plus placement, and leave Phase 4–6 actions visibly disabled.
- **Return paths:** login accepts only a relative path beginning with one `/`; protocol-relative paths, absolute URLs, backslashes, encoded slash/backslash separators and `javascript:` input fall back to `/`. The proxy forwards its own validated current-path header to protected server layouts so deep scan paths survive both proxy login and server-side session recovery.
- **Bootstrap shell:** the Phase 0 shell uses a mobile navigation drawer below 768px, a compact icon rail from 768px, and the full sidebar from 1024px. The root placeholder is the only current route; future navigation labels remain disabled until their scheduled features exist.
- **Status board UX:** card grid + table toggle; filters (department, category, status, location); each status shown as **icon + text + colour** (never colour alone); auto-updates through SSE.
- **Calendar:** week/day timeline per machine; drag-to-select slot; conflicts shown inline from the availability endpoint.
- **Tablet-first for wards;** large tap targets for check-in/out.
- **Loading/empty/error states** designed for every list.

## 11. Environments & deployment

| Env | Web | API/Worker | Neon branch | Redis |
|---|---|---|---|---|
| Local | `next dev` | `nest start --watch` | `dev` | docker-compose |
| Staging | Vercel preview/staging | Azure App Service (staging slot) | `staging` | Staging instance |
| Production | Vercel production | Azure App Service (+ worker) | `main` | Production instance |
| CI | build only | hermetic by default; explicit integration path uses real services | ephemeral branch for explicit integration only | service container for explicit integration only |

**Migrations:** `prisma migrate deploy` runs as a pipeline step *before* the new API version receives traffic; migrations must be backward-compatible with the previous release (expand → migrate → contract).

**Health:** unversioned `GET /health` (liveness) and `GET /health/ready` (Neon + Redis) stay at the root so host probes and uptime monitoring do not depend on an application API version. Both checks are bounded to about one second. Database failure or timeout returns HTTP 503 with overall status `down` because Neon is the system of record. Redis failure alone returns HTTP 200 with overall status `degraded`; liveness remains independent of both services.

**Database connections:** Prisma 7 uses the `@prisma/adapter-pg` driver adapter with the pooled `DATABASE_URL` for API traffic. `prisma7.config.ts` uses the direct `DIRECT_URL` for migrations and other CLI operations. Prisma connection startup is non-blocking so an outage is represented by readiness instead of preventing liveness; shutdown disconnects the client gracefully. The long-lived Neon branches are `dev`, `staging`, and `main`. Explicit database integration jobs create temporary children of `dev`, apply committed migrations with the direct URL, use the pooled URL at runtime, and remove the branch after the run.

**Foundation CI:** pull requests to `main` and pushes to `main` run one required `Quality` job: frozen pnpm install, format check, lint, typecheck, tests, then build. Jest and Vitest provide deterministic localhost test configuration internally, so the default test suites never consume developer environment files or contact Neon/Redis. Prisma Client generation is automatic before build, typecheck, and test. The build step receives only safe localhost URLs needed by startup validation. Real Neon branches and service containers are reserved for explicitly selected integration paths.

**Supabase Auth environments:** local Auth uses Site URL `http://localhost:3000` and the sole
redirect allow-list entry `http://localhost:3000/**`. Exact staging and production URLs are added
only after those domains exist; Vercel preview wildcards are forbidden. The web receives the modern
publishable key, while the modern secret key stays API-only. Supabase's database remains empty of
application tables because Neon is the system of record.

**First administrator bootstrap:** `BOOTSTRAP_SUPER_ADMIN_EMAIL` is an optional API-only deployment
secret. When no active, non-seed SUPER_ADMIN exists, a valid token for that exact address may create
the initial row only after the Supabase Admin API confirms the address. A PostgreSQL advisory
transaction lock makes simultaneous first requests safe. Seed addresses and `.invalid` domains are
rejected, and the setting becomes inert as soon as a real active SUPER_ADMIN exists. Normal users
are created with their Supabase identity by the Task 2.5 invitation workflow. `last_login_at` uses a
conditional update at most once per five minutes per user.

The disposable Task 2.2 proof does not modify any long-lived branch. The real first administrator
is bootstrapped once against Neon `dev` now that Task 2.4 supplies the web login flow, using the real
address only in the API's ignored `.env`. Production repeats the same one-time operation with
`BOOTSTRAP_SUPER_ADMIN_EMAIL` supplied by the deployment secret store, then removes the setting.

## 12. Security & privacy

- No patient data stored; purpose fields carry a UI warning and are excluded from logs.
- One-hour ES256 JWTs; the global guard verifies JWKS signature/key ID, exact issuer, authenticated audience and token role, expiry, and UUID subject. It rejects alternate algorithms, anonymous/service-role tokens, and all malformed Bearer headers; application roles come from Neon, never from JWT claims.
- Helmet, strict CORS (`WEB_ORIGIN` only through an exact origin predicate; other origins receive no allow-origin header), Redis rate limits, body size limits, upload type/size allow-list.
- Private storage buckets, signed URLs (≤5 min), virus-scan hook point documented for uploads.
- Secrets only in host/Vercel/GitHub secrets. The modern Supabase secret key never reaches browser code or build assets; only `NEXT_PUBLIC_SUPABASE_URL` and the publishable key are public.
- Supabase SSR stores access and refresh tokens in its `sb-<project-ref>-auth-token` cookie (chunked when necessary). Supabase requires the browser client to read the refresh token, so these cookies are deliberately **not HttpOnly**. They use `SameSite=Lax`, `Secure` outside localhost and path `/`; compensating controls are the one-hour access-token lifetime, refresh-token rotation, strict same-origin bearer attachment and the Content-Security-Policy scheduled for Task 10.2. Authenticated responses that refresh cookies carry private/no-store cache headers.
- Audit log is append-only and Admin-visible.
- Dependency audit in CI; Dependabot enabled.
- Backups: Neon point-in-time restore window documented and a restore drill performed (Task 10.4).

## 14. Testing strategy

| Layer | Tool | What must be covered |
|---|---|---|
| Unit | Jest/Vitest | State machines, status derivation, booking rules, permission map |
| Integration (explicit) | Jest + ephemeral Neon branch or Testcontainers + Redis | Repositories, **exclusion constraint**, transactions, cache invalidation; never part of the hermetic default suite without an explicit integration path |
| Concurrency | Jest | N parallel bookings for the same slot ⇒ exactly one succeeds; parallel check-outs ⇒ one succeeds |
| API e2e | Supertest | Auth, permissions (403s), validation (400s), conflict (409s) |
| UI e2e | Playwright | Login → find machine → see status → book → check-out → check-in → report fault → technician resolves |
| Resilience | Jest | Redis down ⇒ API still correct |
| Load | k6/Artillery | Status board under N concurrent users; booking under contention |

The Task 2.6 Auth/RBAC contract keeps one hand-written access row for every production controller
handler plus the non-production Swagger infrastructure routes. Each row declares unauthenticated,
inactive and all-six-role outcomes independently of the shared permission map. Runtime discovery
must match that manifest exactly and every controller handler must declare exactly one of
`@Public()`, `@AuthenticatedOnly()` or `@RequirePermission()`. This makes both a new unclassified
route and a permission-map mutation fail the hermetic e2e suite. JWT tests use local ES256 keys and
a loopback JWKS endpoint; no hosted Auth, Neon or Redis service is contacted. Strict authorization
accepts only the case-sensitive `Bearer` scheme. A denied `HEAD` request proves the same status and
request-ID header as `GET`, but has no JSON body because HTTP suppresses bodies for `HEAD` responses.
